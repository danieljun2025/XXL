## 一、Prompt 正文

你是一名资深全栈工程师兼测评产品设计师。请为我设计并实现一个**职业锚（Career Anchor）在线测试**网站，用来替换仓库中现有的消消乐小游戏。请分两阶段：**阶段 A 只输出设计文档，等我确认后再进入阶段 B 开发**。

### 1. 背景与目标
- 理论基础：Edgar Schein 的职业锚理论，共 8 种职业锚：
  1. TF 技术/职能型（Technical/Functional Competence）
  2. GM 管理型（General Managerial Competence）
  3. AU 自主/独立型（Autonomy/Independence）
  4. SE 安全/稳定型（Security/Stability）
  5. EC 创业/创造型（Entrepreneurial Creativity）
  6. SV 服务/奉献型（Service/Dedication to a Cause）
  7. CH 挑战型（Pure Challenge）
  8. LS 生活方式型（Lifestyle）
- 目标：测试者输入「姓名 + 邮箱」后答题，完成后**立即看到个人结果报告**；结果被**永久保存**，可以事后再查看；同时支持**很多人同时在线作答**。
- 使用场景：团队/培训/辅导中批量发放链接，管理员事后能汇总查看。
- 界面语言：简体中文（预留 i18n 结构，不强制英文）。

### 2. 用户身份与并发
- 无需注册密码，以 **「姓名 + 邮箱」** 作为身份：
  - 邮箱统一转小写、去首尾空格后作为唯一标识（`email_normalized`）；姓名仅用于展示，允许重名。
  - 同一邮箱再次进入：提示「检测到你已有记录」，提供 ① 查看上次结果 ② 重新测试（保留历史，新增一条）。
- 邮箱格式校验（前后端都要做）；姓名 1–30 字符。
- **查看密钥（取代邮件验证，v1 不做任何邮件发送）**：
  - 首次测试时，测试者在「姓名 + 邮箱」之外**自设一个查看密钥**（建议 6–32 位，需二次输入确认，页面提示"请牢记，系统不会发邮件找回"）。
  - 服务端只存**加盐哈希**（argon2id / bcrypt / scrypt 任选其一），绝不存明文、不写日志。
  - 之后凭「邮箱 + 查看密钥」才能查看历史结果、继续未完成的作答、重新测试；密钥错误统一提示"邮箱或密钥不正确"（不泄露邮箱是否存在）。
  - 同一邮箱的所有测试共用同一个密钥；已存在的邮箱再次"首次进入"时，必须先输入原密钥验证，通过后才能继续，不能用新密钥覆盖。
  - 暴力破解防护：按「邮箱 + IP」限速，连续失败 5 次锁定 15 分钟（锁定时间可配置）。
  - 忘记密钥：无邮件找回，由**管理员在后台重置**（重置后测试者重新设置密钥，历史结果保留）。
  - 验证通过后发放短期会话 token（如 2 小时，HttpOnly Cookie 或内存中的 Bearer），后续接口凭 token 访问，不重复提交密钥。
- **并发要求**：每个测试者的作答进度互不影响；服务端无全局可变状态；写入使用事务/唯一约束保证不重复；预估同时在线 200 人以内，需说明如何扩展到更多。
- **断点续答**：答题过程中每题自动保存草稿（服务端或至少 localStorage），刷新/关闭后用同一邮箱可继续。
- 基础防刷：同 IP 限速、提交接口加简单的 rate limit；同一人短时间重复提交去重。

### 3. 测评内容
- 题库：采用经典 **40 题职业定位问卷结构**（8 个维度 × 每维度 5 题），每题 1–6 分李克特量表（1=从不 … 6=总是）。
- **版权提醒**：Schein 原版问卷有版权。请**自行撰写原创题目文字**（贴合中文职场语境，每个维度 5 题，覆盖该维度的核心表现），不要逐字复制原版题目。题库放在独立的 `questions.json`，便于我后续修改。
- 题目顺序：每位测试者随机打乱（固定随机种子存入记录，保证可复现）；一页一题或一页 5 题（移动端优先，请给出建议并实现可切换的配置）。
- 计分规则：
  1. 每个维度的 5 题得分求平均；
  2. 附加环节（可选配置开关）：答完 40 题后，让测试者从所有题中选出**最认同的 3 题**，这 3 题所属维度各加 4 分后再求平均（沿用经典算法）；
  3. 输出 8 个维度的得分（保留 1 位小数）、排名；**得分最高的 1–2 个维度为主职业锚**；并列时都展示。
- 所有计分逻辑写成**纯函数**，放在独立模块，并附单元测试（含边界：全 1、全 6、并列、缺题）。

### 4. 结果报告（完成后立即返回）
页面需包含：
1. 姓名 + 完成时间 + 报告编号；
2. 主职业锚（1–2 个）：名称、一句话定义、核心动机、典型优势、潜在盲区、适合的岗位/环境、发展建议、不适合的环境；
3. 8 维度雷达图（或条形图，优先保证移动端可读）+ 得分表；
4. 次要职业锚简述（排名 3–4）；
5. 免责声明：测评为自我认知参考，不构成录用/诊断依据；
6. 操作：打印/保存为 PDF、重新测试、退出（清除会话）。
- 各职业锚的解读文案放在独立文件 `anchors.json`，请你**原创撰写**，语气专业、积极、非评判。

### 5. 数据保存
每次测试保存一条完整记录：
```
participant: id, name, email, email_normalized(唯一), key_hash, failed_count, locked_until, created_at
attempt:     id, participant_id, status(draft|submitted), question_order(seed),
             answers(JSON: 题号→分值), top3_picks, scores(JSON: 8维度),
             primary_anchors, started_at, submitted_at, user_agent, ip_hash
```
- 一个 participant 可有多个 attempt（保留历史，不覆盖）。
- IP 只存哈希，不存明文；邮箱仅用于识别身份，v1 不发送任何邮件。
- 管理员后台（需口令保护，口令走环境变量）：
  - 列表：姓名、邮箱、状态、主职业锚、提交时间，支持搜索/筛选/分页；
  - 查看单人完整报告；
  - **导出 CSV / Excel**（含 8 维度得分）；
  - 简单汇总：各职业锚人数分布；
  - 删除某人数据（满足隐私删除请求）；
  - 重置某人的查看密钥。
- 备份：说明备份与恢复办法。

### 6. 技术约束与选型
- 现状：仓库是纯静态站（GitHub Pages，含 `CNAME`），**纯静态无法做到多人共享保存**，必须引入后端。请在设计文档中比较并**推荐一个**方案，并给出理由与成本：
  - 方案 A（默认推荐）：静态前端 + **Supabase**（Postgres + Row Level Security + Edge Function 做密钥校验），部署简单，免费额度够用；
  - 方案 B：Cloudflare Pages + Workers + D1；
  - 方案 C：Node/Express + SQLite/Postgres，自建部署。
- 前端：尽量轻量（原生 JS 或 Vue/Preact 均可，需说明理由）；移动端优先；无障碍（键盘可操作、对比度达标）。
- 邮件：**v1 不做**，数据模型和接口不要依赖邮件；后续如需再加，作为独立里程碑。
- 保留原游戏：把现有 `index.html` 移到 `/game/`，新测试放站点根目录，避免丢失。
- 安全：输入校验与转义（防 XSS）、参数化查询（防注入）、HTTPS、CORS 限定、管理员口令限速、会话 token 随机且短期有效，所有结果接口必须校验会话归属。

### 7. 阶段 A 交付物（本次只做这些，不写业务代码）
请输出一份设计文档（Markdown），包含：
1. 方案选型对比与最终推荐；
2. 页面清单与流程图（欢迎页 → 填姓名/邮箱/设置密钥 → 答题 → 提交 → 报告；回访流程（邮箱+密钥）；管理端）；
3. 数据库表结构（含索引、唯一约束）与 API 列表（路径、入参、出参、错误码，含「设置/验证密钥」「锁定」「管理员重置密钥」）；
4. 40 题题库草案（原创）与 8 个职业锚解读文案草案；
5. 计分算法伪代码 + 测试用例清单；
6. 并发、隐私、防刷的具体措施；
7. 目录结构、开发里程碑（建议 M1 骨架 → M2 答题与计分 → M3 报告 → M4 存储与密钥验证 → M5 管理后台 → M6 部署）；
8. 风险清单与我需要提供的东西（域名、管理员口令等）。

**等我回复「确认」后，才进入阶段 B（开发），并按里程碑逐步提交。**
